# E3-P3-B2-D - Append-only persistence and migration proposal

Date: 2026-10-30 (Asia/Bangkok). **DESIGN-ONLY / PARTIAL_DESIGN**. Names and constraints below are proposals, not installed schema. No SQL/Alembic migration is delivered or executed. SOURCE_CLAIM remains INACTIVE.

## 1. Storage principles and existing contract boundary

Preserve all existing tables, evidence vocabulary, identity uniqueness, audit actor rules, version checks and append-only history. New normalized relations carry important identities and event references; canonical JSON carries only bounded snapshots/metadata. New proposal/approval records do not change a candidate's status or create CandidateReview/MappingReview decisions.

All new business rows are insert-only. Revocation, supersession, person equivalence and key rotation append new events; no UPDATE/DELETE/TRUNCATE of events, evidence, receipts, reviews or provenance. The new insert-once guard has no mutable cursor or domain state. Current views derive latest valid state by an authenticated sequence/chain, never MAX(timestamp), UUID ordering or arbitrary JSON flags. Existing candidate/identity roots can change only under separately approved finalization/compensation contracts.

Use existing UUID, timestamptz, text, integer/bigint and JSONB conventions; RESTRICT foreign keys; nonblank and JSON-shape CHECKs. Sequence numbers are stream order, not an optimistic `version` column on immutable events. Preserve the frozen SQLAlchemy naming convention; explicit names for composite/partial indexes. No new shared mutable Base mixin or alteration to frozen schemas is assumed.

## 3. Enforcement allocation and append privilege

| Invariant | Required database enforcement | Required transactional validation |
| --- | --- | --- |
| Referential identity and same proposal/pair/version/policy | PK, RESTRICT FK and explicit composite FK/UNIQUE targets on new tables | Reread current candidate/source context and compare to original |
| Event type, nullability, branch/assurance shape | Row CHECKs with explicit NOT NULL; typed-reference constraint triggers/functions for cross-row kind | Strict request/envelope allowlist and policy evaluation |
| Distinct historical actor/human | NOT NULL FKs and approval/compensation row CHECKs | Current person-equivalence closure and current binding/grant/auth_version |
| Single approval/finalization | UNIQUE(proposal_id); UNIQUE(candidate_id,candidate_version); original operation-key uniqueness | Lock order, replay command digest and authorization on retries |
| Single approved Scopus author owner | Existing `uq_identities_scopus_author_approved` stays unchanged | Lock author/candidate and verify negative/history/ownership guards |
| Append-only and trusted timestamp/signature | No direct INSERT/UPDATE/DELETE/TRUNCATE for ordinary web/ingestion roles on history tables; reviewed restricted append functions/writer role; forbid mutation triggers on new immutable tables | Trusted action identity, policy/source/current authority verification and protected signer |
| Canonical bytes/hash consistency | New-table byte-digest check via separately approved available DB hashing mechanism; signed envelope and typed-column correspondence in append function | Exact encoder, schema/domain separation, duplicate-key rejection and signer verification |
| Atomic decision/root/review/audit/assurance | One transaction, reviewed deferred constraint triggers on new sidecar links, existing root uniqueness/version constraints | Complete write-set validation before return; caller commit; no independent audit commit |

Cross-row rules cannot safely be hidden inside ordinary CHECK expressions. PostgreSQL documents that CHECK is not intended to enforce other-row data; use FKs/uniqueness and reviewed constraint triggers/functions for these relationships. This is design rationale, not executed constraint evidence. [PostgreSQL 16 constraints](https://www.postgresql.org/docs/16/ddl-constraints.html).

New functions, if chosen, require pinned search_path, schema-qualified objects, no PUBLIC EXECUTE, no caller-selected SQL/path/issuer, narrowly owned privileges and a review against privilege escalation. The web role must not SET ROLE to an arbitrary history writer. The append interface verifies canonical envelope/typed column equality and does not become a generic signed-JSON insert API. DBA/superuser can bypass ordinary database controls; external checkpoints and independent key custody provide additional detection, not magical prevention.

The current AuditService scaffold is not this writer. Existing direct AuditEvent construction must be reconciled in an explicitly authorized later implementation. B2-D does not centralize it or rewrite old history. New audit rows retain USER/SYSTEM invariants; a SYSTEM ingestion event cannot be reused as human approval.

## 4. Event transitions, timestamps and replay

PROPOSE appends proposal/context/provenance/authority refs, domain event, audit and outbox; candidate stays PENDING. AUTHORIZE appends exactly one distinct-human exception approval and matching event/audit/outbox; still no candidate decision. FINALIZE is the only new source decision transaction. CANCEL/SUPERSEDE of an unfinalized proposal terminates its usability without CandidateReview REJECT/REOPEN. Do not reuse existing frozen action values for pending history.

Each stream sequence is allocated under the existing guard and stream consistency checks, with UNIQUE conflict as a backstop. The first predecessor is explicitly null; subsequent predecessors and hashes must point to the actual last committed/action-visible event. Event sequence, not timestamp, orders actions. Allocate original event UUID and DB time inside the guarded transaction; canonicalize/sign once; enforce approved timestamp origin in the append boundary. A UUID or DB time alone does not authenticate a human action.

Event hash input: domain/version, event UUID/kind/stream sequence, previous hash, exact policy digest, context digest, proposal/approval/target references, actor identities/binding/grant/auth_version, bounded reason/risk, original server time, operation key/command digest, authority receipt/checkpoint references and preallocated audit UUID. Exclude the event's own hash/signature and the audit payload to avoid recursion. Audit metadata contains the event ID/hash. Signer verification authenticates the envelope; hash recomputation alone does not.

Replay has two distinct meanings. Historical verification loads immutable original bytes by event ID, verifies signature/chain/relations and retains original time even after a later revocation. Operational reuse additionally authenticates the present caller, checks terminal/superseded state, TTL, active compatible policy and every CURRENT relevant receipt/principal/grant/source revision. A valid old event is not necessarily executable today. A proposal digest supplied by a client is a comparison hint, not an authority input.

Security-relevant changes to pair, candidate version, selected sources/rules, reason, principal/grant revision, complete assessment set, branch or policy invalidate the old context and require a new proposal. New feed checkpoints with identical scoped members may confirm freshness without rewriting the proposal; their references go in the new authorization/finalization event. Do not include an unrelated global feed counter in semantic equality or silently replace security-relevant receipt revisions.

## 5. Idempotency and duplicate handling

Operation keys are bounded opaque request keys, scoped by authenticated actor account and action kind. Command digest includes action, target candidate/proposal/version, original policy, normalized reason/risk and intended immutable input references; never client-supplied authority truth or client clock. Reuse with a different digest fails IDEMPOTENCY_KEY_REUSED (proposed code). Exact retries return the same stored historical action ID/result only after current access authorization; they do not append new events or recreate audit rows.

Approval has a business UNIQUE(proposal_id) independently of request key. A second different approver cannot append a competing success after the first one; return a stable already-authorized conflict to an authorized caller. Revoked/expired approval is never overwritten or renewed under the same proposal: append cancellation/supersession and require a new proposal. FINALIZE has independent uniqueness per proposal and candidate version; differing request keys/accounts cannot bypass it. Existing approved-owner uniqueness prevents cross-candidate duplicated canonical ownership.

A lost response after outer commit is handled by loading the authorized prior operation result, not by rerunning a new decision. If the outer transaction rolled back, no success exists; retry starts fresh using the original operation key with current validation. A historically committed association may later be suspended/revoked; retry can report that history and current lifecycle state, never falsely report a new current acceptance.

Under the guard, detect an authorized exact historical operation retry before invoking prospective PENDING/no-prior-review checks. Otherwise a legitimately committed decision would always fail those checks. Historical response access is not a new finalization: current usability/revocation is reported separately, and it cannot override the original immutable result.

## 6. Concurrency protocol and revocation boundary

Proposed first release: one permanent ICTU guard row, locked FOR UPDATE, using READ COMMITTED. Acquire it before all relevant domain reads/writes, then use a fresh identity map and reread authoritative state. Retain it through the caller's outer commit. No relevant writer can change the guarded local facts while it is held. This only holds if **every writer** participates; it is not an isolation property granted by a savepoint.

The guard key is fixed by approved server policy, not supplied by a caller. A missing guard row or unavailable lock denies the action; never lazily create a replacement guard or continue without a lock.

Mandatory writer inventory for later integration: source ingestion/reanalysis/activation, candidate source-generation writes, policy activation, issuer/receipt/checkpoint/key changes, grant/binding/person-equivalence changes, User role/is_active/auth_version updates, legacy candidate ACCEPT/REJECT/REOPEN, identity APPROVE/REVOKE/REOPEN and all operational CLIs/direct writers. Code changes and database permission fencing for these paths are a release blocker, not part of this design gate. A writer that cannot acquire the guard or be fenced makes this design unfit for activation. Legacy partial uniqueness alone does not protect stale source/permission reads.

Lock order for participants: (1) ICTU guard; (2) affected User rows sorted UUID; (3) lecturer rows sorted UUID; (4) candidate rows sorted UUID; (5) ScopusAuthor rows sorted UUID; (6) existing identity rows sorted UUID; (7) any additional documented coordination locks. Acquire only after classifying targets from IDs, then reread bound content and validate. Do not lock candidate before the guard in one path and after it in another. Missing identity rows are protected by the author fence, guard and existing partial unique index, not a nonexistent-row lock. Deadlock/lock timeout fails closed; no automatic branch fallback.

Guard readers also verify current source generation/state and exact B2-B hashes, active policy, complete fresh authority feeds, current principal equivalence, stored RBAC/auth_version, capabilities, proposal/approval chain/TTL, all hard conflicts and ownership. Expiry is evaluated at the database-derived guarded decision instant. Security guarantee: facts valid at this local decision instant, with guard retention to commit and a bounded outer transaction. Do not claim expiry cannot occur between validation and physical commit. Ratify this ordering/freshness model (D04/D09), including a finite transaction timeout; otherwise release is BLOCKED.

Remote revocation is effective locally when its authenticated ledger append commits under this guard. Earlier local revocation must deny; later local revocation orders after the decision and triggers suspension/compensation assessment. A remote change not yet imported is bounded only by the accepted feed-lag SLA. Guard coverage, feed health and explicit complete-set receipts are necessary; fetching a remote callback under an ordinary transaction does not make remote revocation atomic.

PostgreSQL READ COMMITTED permits different statements to see different committed states, while conflicting row locks coordinate participating transactions. This motivates the guarded reread protocol. It must be proven with two-connection schedules and writer-coverage tests, rather than presumed correct. [PostgreSQL 16 isolation](https://www.postgresql.org/docs/16/transaction-iso.html), [explicit locking](https://www.postgresql.org/docs/16/explicit-locking.html).

## 7. Caller transaction ownership and atomic finalization

The caller owns the outer connection/transaction, isolation setup, commit/rollback and any full retry. Future action service borrows that connection through an isolated ORM identity map and an explicitly owned savepoint with autoflush disabled. It flushes only its own action write-set. Release its savepoint on success; roll back its savepoint on semantic/ordinary statement failure. Never call parent flush/expire/commit/rollback/close. Never use parent Session.begin_nested() as a way to preserve pending objects: SQLAlchemy documents that it flushes pending state unconditionally. [SQLAlchemy transaction documentation](https://docs.sqlalchemy.org/en/20/orm/session_transaction.html#using-savepoint).

Read-only V1 helpers remain unchanged. For a future write helper, a pending/mutated parent ORM object touching candidate/source/account/identity authority inputs is an incompatible caller context and must be refused before mutation, not silently flushed or ignored. Prior unrelated caller writes and pending objects must survive action-local failure and retry. A caller that has already taken relevant locks out of order must not enter this protocol; caller integration is reviewed explicitly. Raw SQL by an unrestricted malicious caller cannot be made safe by an ORM convention; DB writer fencing is required.

SAVEPOINT cannot promise to preserve a transaction after connection loss, outer transaction abort or an error requiring a full-transaction retry. Propagate these failures and let the owner decide a full rollback/retry; do not falsely return a reusable parent or retry only the child after serialization failure. No service-wide catch-all IntegrityError -> duplicate success. Validate SQLSTATE/constraint identity and reload a prior action only when its exact idempotency/authorization conditions are met.

Proposed finalization sequence, entirely within one caller-owned outer transaction:

1. Require server-authenticated active HUMAN actor. Open the owned action savepoint; acquire the guard and remaining locks in order. Reject incompatible caller state and inactive/unapproved release composition. The present inactive submit guard is not removed by this proposal.
2. Load the **stored** proposal and original time/signature; for exception load its single stored approval. Authenticate current actor as original reviewer (STANDARD) or approver (EXCEPTION). Reauthorize all required original/current actors and principal equivalence without requiring possession of another person's JWT.
3. Verify exact candidate version/observation/generation/pair, no prior unsupported source decision/reopen, source completeness/rules/lineage/current state, all hard conflicts, identity ownership/negative history and unchanged D-2 reason policy. Resolve fresh complete local authorities under the guard; compute revision-2 branch. Any security context/branch change requires new proposal.
4. Enforce original proposal/approval TTL, current policy activation, distinct humans/grants, reason/risk, explicit assurance and independent evidence mapping eligibility. Refuse an exception release if consumer assurance integration is unapproved. No canonical SOURCE_CLAIM IdentityEvidence row.
5. Preallocate all action/review/audit IDs. Create the new identity through a reviewed CANDIDATE -> APPROVED transition using existing status/version semantics; preserve the one-approved-owner index. Append only independently justified standard evidence via an approved mapping. Exception appends institutional provenance sidecar only, never fabricated evidence. No existing negative/exact identity is reopened or reassigned here.
6. Update candidate PENDING -> ACCEPTED with optimistic version check; append CandidateReview ACCEPT and MappingReview APPROVE with exact decision snapshot, identity links, actor and reason. Append finalization, ACTIVE assurance, complete authority references, signed event, audit and outbox in the same transaction. New-event deferred linkage validation verifies the planned review/identity/audit relationships and resulting root versions.
7. Flush the action write-set, verify counts/constraints, release only its savepoint. Return an uncommitted action result to the caller. The caller commits once, handles commit-time failures and only then sends a success response. If the caller rolls back, all action rows/root changes/audit/outbox disappear together with that transaction; no external success/checkpoint is emitted before commit.

Do **not** call current CandidateReviewService.accept_candidate/reject_candidate as subroutines: they commit the session (`:790,947`). A later approved implementation must extract/review noncommitting primitives or create an explicitly isolated source finalizer while preserving existing semantics and audit invariants. Current B2-B `_prepare` rejects preexisting identities/history; future execution may reuse its checks but does not silently repurpose the inactive helper as an operative acceptance path.

## 8. Revocation, supersession, assurance and audit integrity

Receipt/key/person/grant revocation appends authority events. Derived current assurance immediately becomes unusable when its required dependency is locally revoked or unresolved; emit a suspension/work item, not a fabricated human association decision. Before production, all approved-identity consumers must honor this status through an approved M2.8 contract extension. Existing consumers do not, so this is a hard release blocker. No automatic root REOPEN/REJECT or historical mutation is introduced.

Human compensation design: append COMPENSATE_PROPOSE referencing the exact original finalization and reason; a distinct currently authorized HUMAN appends COMPENSATE_AUTHORIZE. Under the same guard, COMPENSATE_FINALIZE rechecks original target/current state, both grants/principals, ownership and lifecycle. Append one terminal compensation row, assurance REVOKED/SUPERSEDED and an existing-valid MappingReview REVOKE (APPROVED -> REVOKED) compensating the original APPROVE; update only the mutable identity root/version and append audit/outbox atomically. No silent candidate ACCEPTED -> REJECTED/REOPEN transition: that lifecycle is not supported by this source design. D08 must ratify the resulting candidate-history display and authority for compensation before implementation.

Supersession does not overwrite an old proposal or finalization. A replacement identity/finalization requires a separate human proposal and policy checks. If same-author reassignment is required, the reviewed compensation and replacement plan must satisfy the single-approved-owner index in one ordered transaction; this gate does not authorize that lifecycle. Never delete old evidence/reviews, change original time, relabel an exception as independent, or reuse an approval for a replacement candidate.

Local event signatures and typed DB relations authenticate the recorded append operation within the trusted writer boundary. Stream hash chains expose alteration relative to trusted anchors; external signed checkpoints add later detection of truncation/privileged rewriting. Anchor publication happens **after** commit through the outbox, with append-only deliveries and stable idempotency. It is not a second commit required to roll back application history. Health/age bounds block further decisions during prolonged signer/checkpoint failure. Historical verification and current operational eligibility remain separate. Signer key compromise plus privileged DB modification exceeds the proposed guarantee and requires an incident/compensation procedure.
