Date: 2026-10-30 (Asia/Bangkok). DESIGN-ONLY / PARTIAL_DESIGN. SOURCE_CLAIM remains INACTIVE. **No runtime acceptance test is executed in B2-D.**

Status vocabulary: DESIGNED = test/control and expected evidence specified, not implemented or passing. BLOCKED = a named authority/governance/schema dependency prevents realistic acceptance. ## 1. Threat model

Assets: correct lecturer-author ownership, distinction between independent and institutional-exception assurance, human decisions and their nonrepudiable context, institutional/source integrity, current grants/person equivalence, immutable event history, caller transaction contents, and private source/account data.

Trust boundaries: browser/JWT to authenticated account; account to human registry; organizational source to formal issuer; verifier evidence to qualification receipt; signed feeds to local ledger; local ledger to guarded decision transaction; operation to durable event/audit; app DB to independent checkpoint retention; approved identity to legacy/new consumer. Every crossing requires explicit authentication, scope and version checks.

| Actor / failure | Capabilities considered | Required defense |
| --- | --- | --- |
| External client or malicious REVIEWER | Change IDs, branch, hash, timestamps, reason, payload; replay own or another user's request | Request allowlists, server-derived facts/identity/time, deterministic branch, full lineage and access checks |
| One human with ADMIN and multiple accounts | Different account IDs, stale sessions, generic account management, attempt self-grant | Governed human equivalence, explicit capabilities, separate enrollment/grant custodians, no ADMIN override |
| Two colluding humans | Formally distinct reviewers/approvers; provide convincing institutional claim | Formal issuer authenticity, independent qualification/insufficiency, conflict checks and accountable audit. Two humans alone cannot prove truth; collusion detection remains organizational governance |
| Compromised or stale upstream feed | Forged/expired receipt, hidden conflicting member, withheld revocation, wrong key/scope | Signed complete scoped checkpoints, continuity, bounded freshness, issuer governance and fail-closed import |
| Concurrent legitimate writers | Source change, grant revoke, legacy decision, duplicate approval while finalization runs | All-writer guard and fixed lock order, root/version/uniqueness constraints, atomic current revalidation |
| Faulty adapter / worker | Writes through borrowed session, commits early, treats absence as insufficiency | Narrow read ports/DB privileges, transaction-aware append writer, no remote callback, explicit UNKNOWN and error propagation |
| Database operator / storage failure | Alter/delete rows, restore old backup, truncate chain, cause partial/commit failure | Restricted privileges, signatures, retained checkpoint anchors, restore/quarantine, atomicity. DBA plus signer compromise is outside prevention guarantee |
| Time/network/signer failure | Clock regression, delayed checkpoint, network timeout, unavailable signing key | DB event time/sequence, age/skew bounds, no stale fallback, bounded transaction and inactive release defaults |

Assumptions requiring owner approval: key custody and HR/issuer/verifier custodians remain trusted and independent; local receipt authority is effective at its committed guarded ledger event; remote revocation lag is bounded rather than instantaneous; all relevant writers can be adapted/fenced; frozen-consumer assurance changes can be approved. If any assumption fails, remain INACTIVE. Do not present signatures as proof that a dishonest issuer told the truth.

## 3. Proposed execution stages and evidence requirements

1. Pure policy/canonicalization unit tests with explicitly synthetic keys/receipts: truth table, failure classification, mixed receipt sets, event-domain separation, deterministic ordering, branch/version changes and no weaker selection. These prove code over fixtures, not real institutional authenticity.
2. Authority conformance: each named issuer/verifier/registry/grant source provides a controlled acceptance environment and signed complete feeds with independent expected outcomes. Capture issuer custody/scope, key rotation/revoke, freshness bounds and adjudication. A simulated authority cannot satisfy this stage.
3. Authorized disposable PostgreSQL: keep `tests/db_safety_guard.py` intact, use only an explicitly allowed verified test target and ENVIRONMENT=test; no application DB. If the guard refuses, stop rather than bypass. Exercise actual migrations, constraints, writer privileges, function permissions, JSON/null semantics and upgrade/restore. No target/credential is supplied or contacted in B2-D.
4. Two-connection concurrency: barrier-controlled schedules for T20-T23, T26-T27, with both commit orders, injected failures after each write and lock/SQLSTATE evidence. Audit every existing writer's participation or technical denial; a pure hybrid-vs-hybrid race alone is insufficient. Do not claim SERIALIZABLE/READ COMMITTED safety from SAVEPOINT-only tests.
5. Actual HTTP/JWT: live test application against that disposable DB, real dependencies/cookies/token auth_version, ADMIN/REVIEWER/LECTURER/service/unresolved actors, grants and allowed request fields. Unit extraction of endpoint function bodies is not this stage. Confirm origin/CSRF protections for cookie-authenticated writes; auth mechanism coexistence must be explicitly reviewed.
6. Browser E2E: distinct real test HUMAN principals and accounts, separate sessions, proposal then separate approval, assurance display, conflict/stale errors, revoked permission and duplicate retries; verify server history and identity state from authorized test DB assertions. No real lecturer or reviewer data.
7. Independent security review and explicit release decision. Current code submit remains INACTIVE throughout design and until a separately authorized implementation/release changes it.

Required evidence for each case: exact command/tool and selected node IDs, environment/engine versions, synthetic-vs-real authority classification, target safety verification, input/receipt/context/policy hashes, expected vs observed outcome, status/SQLSTATE, DB before/after counts and identity versions, event/audit links, transaction/lock ordering, screenshot/request evidence where appropriate, failures/skips and limitations. Record DESIGNED/BLOCKED/NOT_EXECUTED now; replace with measured runtime evidence only in a later authorized gate.

## 4. Acceptance exit criteria (not met by this design gate)

All D01-D10 governance/schema/freeze choices ratified; no unset freshness parameter; real authorities/keys/complete feeds available; all writer and consumer coverage proven; PostgreSQL constraints/transaction/race suites executed; actual HTTP/JWT and browser E2E executed; no unresolved high-severity security finding; independent reviewer signs the release evidence. Any unavailable authority, missing audit integrity, hidden branch fallback, same-human bypass, unsupported lifecycle or implicit activation blocks release.
