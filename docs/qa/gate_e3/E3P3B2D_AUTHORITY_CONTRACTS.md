# E3-P3-B2-D - Proposed authority contracts

Date: 2026-10-30 (Asia/Bangkok). DESIGN-ONLY / PARTIAL_DESIGN. No production adapter is supplied. SOURCE_CLAIM remains INACTIVE.

## 1. Trust map and unresolved ownership

| Authority | Required authoritative source | Available now | Owner decision |
| --- | --- | --- | --- |
| Institutional Source | Formally issued ICTU declaration with authenticated issuer delegation, exact artifact scope and revocation feed | Staging has bytes/digests/lineage; no demonstrated formal issuance authority | Nominate ICTU source custodian, authenticated issuance channel and signing keys |
| Independent Identity Evidence | Governed verifier backed by independent author-specific primary evidence and approved qualification rules | Typed verifier-output port only; enum/DOI/ORCID labels do not verify authorship | Nominate verifier operator, source tiers, qualification procedures and conflict-resolution governance |
| Human Principal Registry | ICTU HR/enterprise identity custodian proving person/account equivalence and HUMAN vs SERVICE classification | User accounts have no such registry | Select actual system/export and governed account-binding process; do not assume HR API exists |
| Reviewer/Exception Authorization | Independently governed capability grants bound to current person, account, scope and permission | Existing ADMIN/REVIEWER roles only | Nominate grant custodians, dual-control enrollment/revocation and approver qualification |
| Authenticated History | Restricted local append writer, authenticated event signer and independently retained checkpoints | AuditEvent table; audit service scaffold and multiple direct service writers | Approve actual writer/signer/checkpoint operators and reconcile the single-writer contract |

Every source above is a required authority specification, **not an assertion that the organization has provisioned it**. Missing custodian, trust root, feed completeness or approved policy -> BLOCKED. Test authorities remain test-only and cannot be selected by runtime configuration as a fallback.

## 2. Shared receipts, completeness and validation

The future application consumes validated immutable references from a local ledger. External acquisition/import is a separately authenticated, auditable transaction. The request browser cannot provide issuer facts, independently_verified flags, human IDs, permissions, evidence payloads, event times or authority revisions.

Proposed logical interfaces (documentation signatures, not runnable implementation):

| Port | Input | Output / denial |
| --- | --- | --- |
| InstitutionalSourceAuthority.resolve | Exact candidate context, complete selected source-trace set, decision instant, local authority revision | Artifact-bound issuance receipts or authenticated UNVERIFIED status; deny unknown/stale/revoked/incomplete |
| IndependentIdentityAuthority.assess | Exact pair, source/rule digests, approved qualification-policy digest, complete assessment scope, decision instant | Complete assessment-set receipt plus typed member receipts; no match is an authenticated INSUFFICIENT result, never a missing adapter |
| HumanPrincipalRegistry.resolve | Server-authenticated account IDs, decision instant, complete registry checkpoint | HUMAN linkage/equivalence receipts or explicit SERVICE/UNRESOLVED denial |
| HybridAuthorization.authorize | Authenticated actor, action, current canonical human, proposal/context digest, decision instant | Scoped capability attestation; explicit deny with stable reason |
| AuthenticatedHistory.load_and_verify | Server event/proposal ID, authenticated reader, expected pair/policy binding | Stored verified envelope/relations and original time, or deny; never reconstruct history from a client JSON/hash |

No port takes the caller's unrestricted writable SQLAlchemy Session. Decision readers use a read-only repository interface or a DB role with SELECT only, while the transaction coordinator controls the separate restricted append boundary. A read-only adapter still reads the same guarded local transaction; a separate autonomous engine would destroy atomicity and is forbidden. No adapter commits, rolls back, closes or flushes the caller connection. Key/signature validation is deterministic over local material, not a remote network callback during finalization.

Each immutable authority event/receipt contains typed identity and scope fields: receipt/event UUID, authority kind, issuer ID, issuer subject key, issuer sequence, schema version, policy/algorithm digest, domain-separated payload digest, issued_at, valid_from, valid_until, issuer key ID, signature, local received_at, superseded/revoked target references where applicable, plus an authenticated feed checkpoint reference. Never store private keys or bearer credentials in receipt payloads.

The canonical representation uses a proposed named `HYBRID_CANON_V2`: UTF-8, fixed JSON field allowlist, lexicographic object keys, explicit array sorting by semantic identifiers, no duplicate keys or nonfinite numbers, integer-only numeric security fields, lowercase UUID/hex, UTC timestamp spelling and no normalization of arbitrary human text after hashing. Store exact canonical bytes alongside JSONB plus digest; JSONB text output is not the canonical encoder. Any change to encoding gets a new version. Signature input binds domain, schema, issuer, policy version, pair/scope, receipt identity and exact payload digest. Public-key algorithm/implementation and key custody require security approval; do not invent a trusted key or accept an algorithm from the request. Unknown key/algorithm fails closed.

An authority checkpoint attests its source epoch, scope, contiguous high-watermark, generation time, completeness and set/root digest. Import verifies sequence continuity, no duplicate issuer IDs with different bytes, signature, configured trust anchor, time bounds and coverage before the ledger is usable. An imported partial feed cannot make an omitted receipt disappear. A complete independent-assessment set identifies every relevant member; active qualifiers, invalid/withdrawn states and unresolved conflicts cannot be cherry-picked away. Stale/absent member resolution is UNKNOWN, not insufficient.

Required policy values: MAX_RECEIPT_AGE per authority, MAX_FEED_LAG, MAX_CLOCK_SKEW, PROPOSAL_TTL, APPROVAL_TTL and MAX_TRANSACTION_DURATION. **All are UNSET in this design, so no policy activation may succeed.** Ratification must set finite positive bounds and time-source rules in the signed policy document. At guarded decision time `t`, require valid_from <= t < valid_until, acceptable issued/received/checkpoint ages, no excessive future timestamp, no clock anomaly, complete scope and current local revocation state. Never refresh an old receipt by changing received_at or using last-known-good after expiry. Validity ordering uses authority sequence/event lineage, not wall-clock timestamps or UUID order.

Revocation imports acquire the same local institution guard as decisions. If their committed ledger event precedes the decision's guard acquisition, the decision must see it and deny. If the decision obtains the guard first, a later local revocation orders after it and triggers compensation assessment. External revocation before ingestion is bounded only by the ratified feed-lag SLA: instantaneous remote revocation is **not guaranteed**. Require owners to accept this security boundary or block release; do not call a cached timestamp globally current.

Proposed error categories: AUTHORITY_UNAVAILABLE (503), AUTHORITY_STALE (409), AUTHORITY_SCOPE_INCOMPLETE (409), AUTHORITY_RECEIPT_INVALID (409), AUTHORITY_REVOKED (409), HUMAN_CLASSIFICATION_REQUIRED (403), EXPLICIT_PERMISSION_REQUIRED (403), HISTORY_INTEGRITY_FAILURE (409). Actual public codes require contract review; retain existing B2-B and auth codes where applicable. Denials expose static messages, no raw source/account details. A timeout, parse error, signature failure or ambiguity never produces an allow result.

## 3. ICTU Institutional Source Authority

Authority: approved ICTU issuer, delegated by a documented institutional custodian. A repository/Craw harvest or source URL is an acquisition channel; its SHA-256 provides integrity, not institutional authentication. A proposed formal issuance can be a signed declaration export or a separately documented authenticated internal attestation over exact bytes. Selection/provisioning of the actual channel is BLOCKED.

Receipt scope includes organization=ICTU, declaration kind, authorized issuing unit, source system, source record and artifact identifiers, artifact/record digests, capture/analysis/claim IDs or an explicitly validated mapping to them, claimed Scopus ID, intended lecturer subject identity, issue revision, validity interval and verification method version. The local verifier recomputes actual artifact bytes/digests, checks B2-B full lineage and that the resolved lecturer subject matches by approved profile URL/email resolution, never name alone. Issuing-unit authority must cover that declaration and period. Subject identifiers in protected storage are not forwarded in public snapshots.

For an exception, every selected active trace/artifact must have current formal verification. Do not quietly drop unsigned selected history to obtain eligibility. For STANDARD, an authenticated current absence of verified issuance may remain explicitly UNVERIFIED context; a revoked selected issuance blocks both branches. Missing/revoked authority status cannot be confused with UNVERIFIED. Unrelated receipts do not override relevant revocation.

Revocation/supersession targets an exact signed receipt and artifact revision. It never updates/deletes staging or reinterprets old bytes. A replacement artifact requires a new capture/analysis/generation and fresh proposal. Compromised issuer-key events invalidate affected scopes under the approved key-compromise rule, quarantine incomplete feeds and suspend finalization until coherent status is restored.

Test design: genuine authorized issuer sandbox fixtures with signed valid/invalid/wrong-issuer/wrong-scope/expired/revoked receipts; altered artifact and record bytes; valid hash with forged issuance; partial selected coverage; equal-time capture incompleteness; rollback of revoked feeds; key rotation/compromise; outage; mismatched lecturer/pair; same bytes under a different source revision. Pure signatures can use explicit synthetic keys only as unit evidence; an actual issuer acceptance gate remains BLOCKED until provisioned and NOT_EXECUTED.

## 4. Independent Identity Evidence Authority

Authority: a named independently governed verifier with an approved versioned qualification policy, not the reviewer who wants the association. Current matching-rule scaffolds are not an implemented verifier. Membership in the existing ORCID_EXACT/DOI_EXACT/PUBLICATION_OVERLAP/COAUTHOR_CONFIRMED vocabulary is necessary context, not proof. APPROVED_ID is not a shortcut through an already-approved mapping; current B2-B preexisting identity protections remain.

Each assessment binds lecturer UUID, catalog Scopus author UUID/claimed ID, precise assessment context and evidence-revision digest, qualification rules, primary-source provenance, author-position/EID/DOI/ORCID linkage where relevant, supporting and contradicting findings, and a verifiable issuer receipt. Different tiers remain distinct: publisher author ORCID, registry authorship declaration, Scopus profile ORCID and institution-copied ORCID. Matching DOI alone verifies a publication reference, not that a particular lecturer authored it. Self-declared source ORCID, names or institutional claims cannot be laundered into independent qualification.

Complete set resolution returns QUALIFYING, authenticated INSUFFICIENT, INVALID, WITHDRAWN, CONTRADICTORY or UNKNOWN (failure, not evidence). Any relevant invalid/withdrawn/contradictory state blocks both branches under retained V1 policy; it cannot disappear because another receipt qualifies. A receipt resolution/supersession policy must explicitly establish which assessments remain relevant; preserve old receipts and do not convert withdrawal into insufficiency without a separately approved resolution event and policy. A checkpoint must prove set completeness for the context before the insufficient-only exception path exists.

Current qualification is evaluated on proposal, approval and finalization. Newly qualifying evidence invalidates an exception proposal rather than relabeling it. Qualification withdrawal blocks a STANDARD proposal rather than falling back to exception. A changed complete-set revision stales the old security context even if the branch stays the same; a new human proposal is required. Stable, still-current receipt revisions may appear in a newer feed checkpoint without rewriting the old event; fresh checkpoint references are captured in the new validation/finalization event.

Revocation is by signed assessment/issuer event, bound to exact scope and monotonic sequence; unresolved key/source compromise denies. No external verifier or rules can override hard ownership/negative-state conflicts. Promotion to IdentityEvidence is a separate reviewed mapping from actual qualified evidence, never automatic from a receipt label.

Test design: approved verifier conformance dataset with independently adjudicated author-specific ground truth; source-type laundering; DOI-only nonauthorship; swapped ORCID positions; incomplete hidden qualifying/conflict members; mixed valid+invalid; verified=false; insufficient vs outage; withdrawal; reassignment; revision/policy mismatch; stale feed; pair substitution. Real verifier accuracy and independence qualification are BLOCKED and NOT_EXECUTED.

## 5. Human Principal Registry

Authority: nominated ICTU person/enterprise-identity custodian, with controlled enrollment and signed account binding. An email uniqueness index, lecturer_id or account display name is not proof of distinct people. Service accounts must be explicitly SERVICE; unknown classification denies privileged human review. Enrollment needs identity proof under a documented process; security grants must not be self-issued by the beneficiary.

Stable opaque human_principal UUIDs avoid placing HR/person identifiers in app snapshots. A binding receipt maps an existing User UUID to a principal and account class with validity, issuer sequence and account lifecycle. Multiple accounts for a person resolve to one current canonical equivalence class. Subject merges append equivalence events; they never update historical snapshots. Resolve both historical actor principals against current canonical equivalence before approval/finalization. If a later merge reveals that reviewer and approver are the same person, deny unfinalized actions and initiate governed compensation assessment for prior finalizations.

Ambiguous/multiple active account bindings, cycles in equivalence, uncertain split, disabled/revoked human or missing complete checkpoint -> deny. A person split/correction requires governed review; no automatic relinking to revive an invalid proposal. Stored User.is_active/auth_version/role are reread in addition to registry receipts. Revoking an account or human invalidates outstanding authorizations; keeping a valid JWT cannot override current registry denial.

Test design: two accounts one human, alias/merge after proposal or after approval, real distinct humans, service account, unresolved person, duplicate active bindings, malicious merge/split, cyclic equivalence, revoked binding, stale checkpoint, disabled account and rotated auth_version. Real custody/enrollment evidence is BLOCKED; HTTP binding and registry integration are NOT_EXECUTED.

## 6. Reviewer and exception approver authorization

Authority: nominated capability custodians operating an append-only grant/revocation process with dual-control issuance. Proposed capability names: STANDARD_REVIEW, EXCEPTION_PROPOSE, EXCEPTION_APPROVE, HYBRID_COMPENSATE. They are not new User.role values. Require active stored ADMIN or REVIEWER, current authenticated HUMAN and explicit scoped capability. LECTURER/SERVICE never qualify. ADMIN has no grant bypass and cannot mint a valid grant via generic account administration.

Each grant binds grant UUID, human principal, account UUID (no automatic cross-account reuse), permission, institution/source/candidate scope, granting authority, validity, policy and revision. Grant attestations at action time additionally bind action, exact proposal/event/context digest and current auth_version. Custodians and target reviewers must be separated in grant issuance; recovery/break-glass behavior is BLOCKED pending approval and has no permissive default. A grant is not an approval of an association.

On proposal authorize its reviewer. On exception approval independently authenticate the approver; load the reviewer identity and original context from the stored proposal, not a second caller-supplied reviewer identity/token. Recheck the reviewer's current account/human/grant without impersonating a session. On finalization, the authenticated triggering human is the original reviewer for STANDARD or original approver for EXCEPTION; both relevant human/grant contexts are revalidated. Distinct account IDs AND canonical human IDs are mandatory. A system worker cannot turn a queued proposal into a human authorization.

Every retry is authenticated and authorized before returning an idempotent prior result; an old success must not leak a revoked user's proposal. Historical success can be reported as a historical decision to an authorized reader without falsely claiming the association is still current. Approval renewal, expired grants, changed principals/scopes and new auth_version require a new action; never patch historical approval bytes.

Test design: grants absent/revoked/expired/wrong account/human/scope/permission; ADMIN with no grant; own grant issuance; JWT replay after password reset; lost reviewer capability between proposal/approval/finalization; current approver with stale proposal; grant custodian compromise; same-human approver; auth-version mismatch; access to idempotent results after revocation. Real grant governance and authenticated integration are BLOCKED/NOT_EXECUTED.

## 7. Authenticated audit/event history

Authority: a restricted transaction-aware append boundary plus an approved event signer; separately governed checkpoint retention detects privileged history changes. Server/database supplies event ID, sequence and original time. Browser-supplied times are rejected. Historical replay loads the stored proposal/event ID and verifies canonical bytes, signatures, chain, foreign-key relations and original timestamp before checking current eligibility. Matching a newly supplied hash never proves history.

An append action obtains sequence and DB time under the guard, builds a canonical envelope, obtains a domain-scoped signature from the approved local signer without an unbounded remote call, verifies it, then inserts history and audit rows atomically. The signer must be separately protected from ordinary web request data and inaccessible for arbitrary signatures; algorithm/key custody remains D06. If the available signer requires network I/O or cannot be made transaction-safe, this synchronous design is BLOCKED until an explicitly reviewed alternative is approved. Do not pre-sign unknown DB times or fabricate signer availability.

Events bind previous event hash, operation/action key, context/policy/snapshot digests, typed actor identities, original proposal/approval references and planned audit UUID. Existing AuditEvent metadata references the resulting event hash; the event does not hash that audit payload, avoiding a cyclic digest. Audit and domain append either both commit or neither commits. No direct generic audit insert is accepted as an authority signature. No change to the existing physical `metadata` column or actor invariant.

After outer commit, an outbox drives independently signed/retained stream checkpoints. Checkpoint delivery status is itself append-only. External anchoring is asynchronous and is **not** claimed atomic with application commit. Local signatures provide event authentication; external checkpoints add later evidence against DB rewrite/deletion/truncation. Finalization requires checkpoint infrastructure within the ratified health/age bound, otherwise denies. Unanchored tails remain an explicitly bounded risk, and DB-superuser plus signer-key compromise is outside the guarantees. A digest chain alone is not authenticity or deletion proof.

Test design: original time changed with recomputed hashes; event inserted without writer signature; absent/misordered/reused chain member; truncated stream vs retained checkpoint; wrong event kind/pair; wrong audit linkage; signer/key failure; complete transaction rollback; checkpoint outage/reordering; retention restore and key rotation; least-privilege attempts to UPDATE/DELETE/TRUNCATE. Actual signer, external retention and DB privilege integration remain BLOCKED/NOT_EXECUTED.
